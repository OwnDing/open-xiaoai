## 本阶段内容

- **按设备配置**：后端 `data/.config.yaml` 新增 `voice_devices`，以 `Device-Id` 为键，支持四项：`output`（是否收服务端音频）、`tts`（TTS 模块）、`room`（房间）、`reply_style`（回答方式）。逻辑在 [voice_devices.py](../deploy/sherpa-tts/xiaozhi-server-overrides/voice_devices.py)，[patch_server.py](../deploy/sherpa-tts/xiaozhi-server-overrides/patch_server.py) 只加三处挂钩。代码里没有具体设备或房间，没有条目的设备行为不变。
- **房间上下文**：有 `room` 的设备，系统提示词的 `<context>` 里会多一行 `Device room`；Hermes provider 精简提示词时保留 `Device room` 和 `Reply style`。
- **完整句子回答**：`reply_style: sentence` 要求至少用一句完整的话回答，解决 P1 发现的单字回答听不清。
- **按设备 Edge TTS**：`tts: EdgeTTS` 的设备用在线 Edge 合成，其余设备仍用 Sherpa。
- 终端配置去掉 `room`，房间只在后端配置一处。

## 发现的问题：远程桌面占用本机音频

用户连着远程桌面时，蓝牙音箱完全不出声：终端、单独的播放进程、浏览器都一样，即使终端以 SYSTEM 身份运行在会话 0。Windows 端点状态正常、未静音，播放时电平表峰值约 0.49。断开远程桌面后立即恢复（08:23 和 08:26 的播放都听到了）。麦克风不受影响，所以唤醒仍能检测到。

P0.5 记录里 21:33 / 21:38 两次原因不明的失声，当时也有一个活动的远程桌面会话，很可能是同一原因。

处理：远程桌面客户端的“远程音频”设成“在远程计算机上播放”（mstsc：本地资源 → 远程音频 → 设置；Mac 的 Windows App / Microsoft Remote Desktop：Play sound → On the remote PC）。用户此前通过远程桌面播放浏览器音频时是有声音的，可能当时用的客户端或设置不同；下次连接时再验证。

另外：音箱重连后，Windows 端点音量从 49% 变成了 100%（蓝牙绝对音量同步），音箱实际音量由它自己的旋钮决定。

## Sherpa 与 Edge 对比（书房蓝牙音箱）

**合成耗时**（同一句话单独合成整句，不是对话里的出声延迟）：

| 句子 | 音频 | Sherpa | Edge |
| --- | --- | --- | --- |
| 明天宁波小雨，气温十八到二十二度，出门记得带把伞。 | 5.6 s | 0.76 s | 1.38 s |
| 书房灯已经帮你关掉了。 | 2.4 s | 0.31 s | 1.22 s |
| 现在是早上八点四十分，今天是十月五号，星期一，国庆假期第五天。 | 7.2 s | 2.99 s | 1.42 s |

**对话延迟**：同一问题“用两句话说说秋天的特点。”每种 3 次，从提问到第一个音频包的时间，Sherpa 中位数 1.36 s，Edge 2.33 s。Sherpa 边合成边推送；Edge 每句整段合成完才发送。

**盲听**：三句话分别用两种引擎合成，响度对齐，在蓝牙音箱上按 A / B 成对播放（终端开着麦克风，即实际使用的通话音质），不告知用户哪个是哪个。用户选 A（Edge），理由是音色和自然度更好。

**实际对话（Edge，6 轮）**：不查设备的问题 1.9～2.5 s 开始出声，查 Home Assistant 的 3.7～4.0 s（Sherpa 同类约 1.2～1.4 s 和 2.3 s）。后端日志确认都由 `core.providers.tts.base`（Edge）合成。用户认为多等约 1 s 可以接受，书房音箱改用 Edge 继续试用。

其他观察：窄带麦克风下仍有识别错误（“那空间置量”），这时模型会反问确认；只说“关机”时模型会追问是哪台设备，不会直接执行。

## 流式 Edge 与播放优化（2026-10-05 09:00–09:50）

用户反馈两个问题：Edge 整句合成完才发送，响应慢；在线问答时播放伴有“哧哧”杂音，而盲听时两种音色都很干净。

### “哧哧”杂音：播放端每秒播空十几次

服务端限速器按每包 60 ms 的实时节奏发送，只在回答开头预先连发 5 包。第一次句间空档之后，客户端就没有了余量，每一包都是踩着点到的，比该播的时间晚几毫秒。终端原来来一包就播一包，于是一段 17 s 的回答会被播空约 200 次，每次几毫秒，听起来就是“哧哧”声。盲听时播放的是完整文件，没有这个问题。

处理：终端加自适应抖动缓冲 `[audio] playback_buffer_ms = 240`。缓冲播空后先攒够 240 ms 再播；回答或提示音结束时不足 240 ms 的部分直接播完。用同一批包到达时间模拟，播空次数从 207 次降到 3～4 次，正好落在句间。用户确认杂音消失。

### Edge 响应慢：每句都新建连接、整段下载

| 阶段 | 实测 |
| --- | --- |
| 建立 TLS / WebSocket 连接 | 0.60 s（每句都要建一次） |
| 发出请求到第一块音频 | 0.16～0.27 s |
| 第一块之后剩余音频到齐 | 约 0.3 s |
| 要求返回 PCM | 服务端直接关闭连接，只能用 MP3 |
| 同一连接连续发请求、空闲 30 s 后再发 | 都可以 |

新增 `edge_stream` provider：每台设备一条预先建好、复用的连接；MP3 边收边经 ffmpeg 解码（`-probesize 32 -analyzeduration 0 -fflags nobuffer -flush_packets 1`，喂入后约 74 ms 出 PCM）；PCM 立即编码成 Opus 发送；第一段在第 2 个字之后的第一个标点处切出；还没出声就失败时退回自带 EdgeTTS。

| 句子 | 自带 EdgeTTS 第一帧 | 流式第一帧 |
| --- | --- | --- |
| 明天宁波小雨， | 1.25 s | 0.25 s |
| 气温十八到二十二度，出门记得带把伞。 | 1.34 s | 0.49 s |
| 书房灯已经帮你关掉了。 | 1.41 s | 0.32 s |

对话里从提问到开始出声（同一问题各 3 次，中位数）：自带 EdgeTTS 2.14 s，流式 1.17 s，和 Sherpa（1.36 s）相当。

### 句间不连贯：Edge 每句头尾的静音

| 引擎 | 开头静音 | 结尾静音 | 句中逗号停顿 |
| --- | --- | --- | --- |
| Edge | 160～200 ms | 约 570 ms | 310～350 ms |
| Sherpa | 60～70 ms | 230～370 ms | 80～120 ms |

每到一段的交界处就多出约 750 ms 空白，比句中的逗号停顿长一倍多。流式 provider 边收边裁：开头只留 30 ms，结尾最多留 250 ms，句中停顿不动（先暂存，后面还有人声就原样放回）。实测裁剪后开头 40～60 ms、结尾 270～290 ms（含 Opus 补齐），交界处约 330 ms。

### 句中偶尔停顿：Docker 虚拟机时钟慢 7.7%

逐包记录到达时间：474 个包平均间隔 64.0 ms，几乎没有短于 60 ms 的间隔；一段 12.6 s 的音频要 13.8 s 才送完，所以 240 ms 的缓冲每约 3 s 就被吃空一次。真机统计也对得上：约 79 s 的回答播空 26 次。

排查过程：

| 检查 | 结果 |
| --- | --- |
| 生产速度（流式 Edge 合成 14.6 s 音频） | 1.71 s 内全部产出，从不落后于实时 |
| 限速器单独测（一次塞 100 包） | 平均间隔 60.0 ms，准确 |
| DEBUG 日志里的“队列从空恢复”（限速器重新计时） | 0 次；服务端日志显示整段回答早已全部入队 |
| 容器里 `sleep(30)`，主机计时 | 32.67 s，容器时钟只有主机的 92.3% |
| 主机时钟 vs 阿里云 NTP（55 s） | 偏差变化 0.005 s，主机准确 |
| 蓝牙音箱播放 20 s 音频，主机计时 | 约 20.97 s（含启动），和主机一致 |
| 虚拟机时钟源 `tsc` → `hyperv_clocksource_tsc_page` → `acpi_pm` | 都是 92.3%～92.7%，无改善，已改回 `tsc`；未写 `.wslconfig` |

结论：Hyper-V 给 WSL2 虚拟机的时间基准本身偏慢（内核日志里 Hyper-V 报告的 TSC 为 806.403 MHz），虚拟机内部修不好。线上小爱走原生 TTS（只收文字），不受这个节奏问题影响。

处理：`voice_devices` 新增 `send_interval_ms`。按设备覆盖这条连接的 `tts_audio_send_delay`（连接配置是每条连接的独立副本），终端设为 50，折合真实时间约 54 ms 一包，比播放快约 10%，缓冲只会越攒越多。复测平均间隔 53.7 ms，33.4 s 的音频 30.1 s 内送完，模拟播放从未播空；真机约 63 s 的回答播空 0 次。用户确认句与句连贯、没有奇怪的停顿。

## 提示音音色与回声保护（2026-10-05 10:00–10:30）

**提示音改用 Edge**：“我在。”等三段提示音原来由 Sherpa 合成，和 Edge 的回答音色不一致。`fetch-assets.ps1` 改为默认用 Edge 晓晓生成 MP3（`-PromptEngine sherpa` 仍可生成 WAV），终端支持 MP3 提示音，并在加载时裁掉头尾静音：

| 提示音 | 原长 | 裁后 |
| --- | --- | --- |
| 我在。 | 1.22 s | 0.61 s |
| 我没听清，再说一遍？ | 2.57 s | 1.97 s |
| 有需要再叫我。 | 1.90 s | 1.28 s |

用户确认“我在”已经是 Edge 音色。

**回声差点被当成说话**：一次唤醒后用户没有说话，超时日志却显示 VAD 最高概率 0.48、麦克风峰值 -20.9 dBFS，离判定阈值 0.5 只差一点。

| 测量 | 结果 |
| --- | --- |
| 用户真实说话（P0.5 语料，同样的前端处理），每句话的最高 VAD 概率 | 中位数 0.97～0.99；低于 0.5 的“句子”同时也低于 0.15，基本是非人声 |
| “我在”的回声 | 约 0.42 s、峰值约 -11 dBFS，VAD 概率 0.88～0.96；之后 1 s 内仍有 0.71～0.91 |
| 声音交给 Windows 到回声进麦克风（100 ms 测试音，5 次） | 208～225 ms；回声高于底噪 10 dB 一直持续到交出后 615～818 ms |

结论：阈值 0.5 对真实说话是合适的，问题出在余音保护太短（原来是交出后约 420 ms 就开始判断）。

处理：`tts_end_guard_ms` 默认值从 400 改为 700；保护期间麦克风的声音不交给 VAD，但会存进预录缓冲，用户抢着说话时开头不会丢。复测：

- 两次唤醒后保持安静，最高 VAD 概率 0.25 和 0.01。
- 听到“我在”立刻提问，“现在几点了？”“我们家有几台设备”都被完整识别；说完后分别 1.41 s 和 1.22 s 开始出声。

**设备身份**：问“你是哪台音箱”时，模型有时说自己是客厅的小爱。原因是线上 Hermes 的 `SOUL.md` 写着“运行在一台小爱音箱上”。房间信息那一行已加强为“此刻你正运行在书房的这台设备上……即使人设里提到别的音箱，也以这里为准”，但仍不稳定。仓库里的 `SOUL.md` 模板已改为多设备说法，等切换到单一后端时再部署到线上 Hermes。按房间执行的指令（“这个房间的灯”→ 书房灯）不受影响。

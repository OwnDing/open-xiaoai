# 跨平台多终端语音接入方案

日期：2026-10-04（Asia/Shanghai）

状态：设计基线。2026-10-04 修订，补充音频前端、蓝牙通话模式风险、多房间扩展路径、房间上下文和分阶段调整。已完成 Windows 指定蓝牙设备的输入验证，尚未开发或部署新终端。

开发在 `feat/voice-terminals` 分支进行，功能测试和实际使用稳定后再合并回 `main`。mini PC 上运行中的服务保持 `main` 版本，新终端独立启停。

## 1. 目标与边界

在保留现有小爱音箱 AI 功能、原生语音输出和使用方式的基础上，把家里的多个音频设备接成独立的语音终端。同一套小智后端接收多个终端的语音，并把回答返回发起请求的终端。

- 每台终端是一个独立的小智设备，单独输入、单独输出：小爱说的回小爱，蓝牙音箱说的回蓝牙音箱。
- 终端按房间部署，并带有所在房间信息，使“把灯打开”这类指令按说话所在房间执行。
- 扩展到更多房间时，不依赖“一台电脑挂多个蓝牙音箱”，见第 4 节设备类型。
- 新程序首先在 Windows 上开发和验收；音频、设备发现和启动管理层保持跨平台边界，Linux、macOS 有实际设备时再分别验收。
- 终端可使用蓝牙、USB 或电脑内置音频设备；输入、输出可分别配置。
- 普通终端的服务端语音合成支持 Sherpa TTS 和 Edge TTS，按终端配置选择；第一版先实现 Sherpa，Edge TTS 在 P3 实施。小爱继续保留原生音色。
- 语音终端与 AI 后端是两个独立角色，可以同机，也可以部署在不同电脑上。
- 后端地址、端口、设备身份和音频设备均可配置，不把 Windows、当前 IP 或容器名写死在业务逻辑里。
- 当前首个硬件验收环境是 Windows 11 mini PC + 京鱼座蓝牙小黑胶；Windows 验收通过不代表 Linux、macOS 已验收。
- 用户确认各终端位于不同房间，基本不会同时听见同一句话。第一版采用独立唤醒，不增加跨房间抢占或“只能一台说话”的全局锁。

现有代码的关键限制：

1. [Rust 桥接服务](../examples/xiaozhi/src/server.rs) 在 accept 循环中等待当前连接结束，一次只处理一个音箱连接。
2. [音频分发](../examples/xiaozhi/xiaozhi/services/audio/stream.py)、`XiaoZhi` 和对话管理包含全局实例，不能直接把多路麦克风混入同一个现有实例。
3. 仓库已有 `--mode xiaozhi` 本机音频入口，但仍无条件初始化小爱桥接，提示语依赖小爱命令，只使用系统默认音频设备，CLI 录音读取与原生 PyAudio 接口也需要适配。它是代码复用基础，不是已经完成的平台产品。
4. [后端 TTS 补丁](../deploy/sherpa-tts/xiaozhi-server-overrides/patch_index_stream.py) 通过进程环境变量全局选择输出方式，不能同时满足小爱本地合成与普通终端接收音频。
5. 当前 [WebSocket 音频协商](../examples/xiaozhi/xiaozhi/services/protocols/websocket_protocol.py) 对返回的 16 kHz 参数与实际 24 kHz 输出存在兼容处理，新终端需明确上下行格式。
6. [Hermes provider](../deploy/hermes/xiaozhi-provider/hermes.py) 的 `response()` 不使用 `session_id`，每次发送该连接的完整对话，因此对话历史已经按连接隔离；但它拿不到设备或房间信息。

已检查的运行中后端会为每条连接建立独立 `ConnectionHandler`、会话 ID、录音缓冲和 TTS 实例；本地 ASR 模型可共享，录音数据保存在连接状态里。`core/connection.py` 在创建 TTS 实例之前已从请求头读取 `device-id`，TTS 在 `open_audio_channels(conn)` 时获得连接对象，因此按设备选择输出方式可行。仍需通过实际双端并发测试验证整个处理链路。

## 3. 目标架构

```text
房间 A：小爱音箱 ⇄ 原有小爱桥接（4399）──────────────┐
                                                    │
房间 B：蓝牙 / USB 音频 ⇄ 电脑语音终端（每设备一个进程）─┼⇄ 小智后端 ⇄ Hermes / Home Assistant
                                                    │       ├─ ASR：SenseVoice
其他房间：ESP32-S3 小智硬件（原生固件，Wi-Fi）───────┘       └─ TTS：小爱原生 / Sherpa / Edge（按设备）
```

后端看到的每台终端都是“一个设备 ID + 一条 WebSocket”。电脑终端严格按小智协议实现，不在后端增加电脑终端专用分支；以后换成 ESP32 或其他设备时，后端只需登记设备。

普通终端直接使用小智 WebSocket 协议接入后端，不接入单连接的 `4399` 小爱桥接。

同机时可配置 `127.0.0.1` 和已发布的服务端口；远程时配置后端主机名或局域网地址。后端继续使用现有容器部署方式，迁移到 Linux 或 macOS 宿主时检查镜像架构、模型、卷和网络配置，不要求终端跟随后端迁移。

音频采集程序在连接音频设备的操作系统原生环境中运行。Docker 部署的是后端，不把跨平台硬件音频支持建立在宿主设备直通到容器之上。

## 4. 设备类型与多房间扩展

| 类型 | 接入方式 | 适用场景 | 说明 |
| --- | --- | --- | --- |
| 小爱音箱 | 现有桥接 | 已有小爱的房间 | 保持原生音色和使用方式，本期不改动 |
| 电脑语音终端 | 直连小智 WebSocket | 电脑所在房间的蓝牙、USB、内置音频设备 | 本方案主要开发内容 |
| ESP32-S3 小智硬件 | 原生 [xiaozhi-esp32](https://github.com/78/xiaozhi-esp32) 固件直连 | 其他房间 | 设备端唤醒，部分板子带回声消除；走 Wi-Fi，不受蓝牙距离限制 |

蓝牙不适合作为横向扩展路径：

- 有效距离基本限于电脑所在房间。
- 单个蓝牙适配器同时维持多路麦克风通话链路通常不可靠，不按此规划；确有需要时单独实测。
- 唤醒词要求麦克风常开，音箱会一直处在通话模式，影响播放音质，见第 8 节。

设备选择建议：

- 电脑旁边：优先选 USB 会议全向麦（自带硬件降噪和回声消除的那类），收音距离和抗回声通常明显好于蓝牙音箱的通话麦，也没有通话模式问题。现有蓝牙音箱可以继续用，但受通话模式限制。
- 其他房间：优先用 ESP32-S3 小智硬件，每个房间一台。
- 每台终端单独配置所在房间、唤醒词和音频前端参数。

## 5. 电脑语音终端设计

### 5.1 进程模型

- 一个终端一个操作系统进程，每台设备一份配置：设备 ID、显示名称、所在房间、输入设备、输出设备、唤醒词、音频前端档位、VAD / 唤醒阈值、后端地址。
- 由一个守护程序负责拉起和崩溃重启；一台终端出错或重启不影响其他终端。
- 进程内只有一个会话，现有代码的全局单例不再是障碍，不做“单进程多会话”重构。

### 5.2 实现基础：先验证上游 py-xiaozhi

仓库的 `examples/xiaozhi` 源自 [py-xiaozhi](https://github.com/huangjunsen0406/py-xiaozhi) 的早期版本，并针对小爱做了大量修改。上游项目采用 MIT 许可，支持 Windows、macOS、Linux，带 Sherpa-ONNX 唤醒、`webrtc_apm` 音频处理和 CLI 模式。

P1 开始前用 1–2 天验证：

- 能否配置自建后端的 OTA / WebSocket 地址和设备 ID，绕过公网激活流程；
- 能否按名称指定蓝牙或 USB 输入、输出设备；
- 唤醒、VAD、Opus 编解码在这台 Windows 上是否正常，CPU 占用是否可接受。

验证通过就以它为基础，补设备绑定、配置、守护和诊断；不通过就按 5.3 的模块边界自建，参考它和现有代码。Windows 打包需要注意 libopus DLL。

### 5.3 公共逻辑与平台适配

沿用项目 Python 3.12+ 技术栈，复用经验证的唤醒、VAD、Opus、小智协议和重连逻辑。通过独立入口与依赖边界，使普通终端不必加载小爱 Rust 扩展或调用小米命令。

建议的模块边界（名称为设计建议，尚未创建）：

| 模块 | 职责 |
| --- | --- |
| terminal/config | 后端地址、设备身份、房间、输入输出绑定、唤醒词、超时配置 |
| terminal/audio | 统一的设备枚举、采集、播放、格式转换、队列和错误接口 |
| terminal/frontend | 音频前端：高通滤波、降噪、自动增益，后续回声消除 |
| terminal/platform | 平台设备标识、设备变化通知、权限与启动管理 |
| terminal/session | 本终端的唤醒、监听、上传、等待、播放、退出状态 |
| terminal/protocol | WebSocket 握手、音频、TTS 事件、取消、连接恢复 |
| terminal/diagnostics | 设备列表、短录音、电平、播放测试及可读错误 |

音频层优先评估 `sounddevice / PortAudio`，通过回调持续读取采样，避免把阻塞采集放到异步网络事件循环中。该库提供 Windows、macOS、Linux 支持；具体依赖版本在实现时锁定并验证。

| 平台 | 首选音频路径 | 部署和验收注意事项 |
| --- | --- | --- |
| Windows | WASAPI 共享模式 | 麦克风权限、蓝牙 HFP、远程桌面音频重定向、运行会话（见 5.7） |
| macOS | CoreAudio | 麦克风隐私授权、稳定的应用身份、蓝牙路由；用户 LaunchAgent |
| Linux | PortAudio 的 ALSA 路径，验证与 PipeWire / PulseAudio 系统的兼容路由 | 蓝牙 profile、用户音频会话和权限；systemd 用户服务 |

PortAudio 并不意味着所有平台有相同的设备标识或原生 PipeWire 支持；若 Linux 蓝牙设备无法通过目标系统的 ALSA 兼容路径可靠枚举与绑定，单独增加音频后端适配，公共协议和对话逻辑保持一致。

第一版先提供 CLI、配置文件与诊断命令，只在 Windows 验收。

### 5.4 设备绑定与采集

- 配置明确的输入和输出设备，不只使用“系统默认设备”。
- 不持久化易变化的设备数组索引；尽可能保存平台稳定标识，并在每次打开时重新解析。
- 音频库未暴露稳定标识时，增加平台解析或“后端 + 名称 + 属性”匹配；匹配歧义时提示选择，不静默切换设备。
- 每终端只打开一次物理麦克风，把同一份采样分发到唤醒、VAD、编码模块。
- 支持设备实际采样率，显式重采样到 16 kHz、单声道 S16 PCM，再按协议编码为 Opus。
- 播放采样率与上行分开管理：当前服务端实际输出为 24 kHz，后端改为如实声明 24 kHz，终端以服务端 hello 返回的音频参数为准，再转换为输出设备支持的格式。
- 使用有界缓冲和背压；蓝牙断开或后端断线时不无限堆积环境音或回答。

### 5.5 音频前端：降噪、增益与回声消除

当前录音没有任何降噪处理。终端在麦克风之后固定加一层音频前端：

```text
麦克风 → 重采样到 16 kHz 单声道 → 高通 + 降噪 + 自动增益（以后加回声消除）
       → 同一份处理后的音频 → 唤醒 / VAD / Opus 上传
```

- 选型：WebRTC 音频处理模块（APM）。跨平台可直接使用的有 py-xiaozhi 自带的 `webrtc_apm`，以及 `livekit` 包的 [`rtc.AudioProcessingModule`](https://docs.livekit.io/reference/python/livekit/rtc/apm.html)（降噪、高通、自动增益、回声消除，按 10 ms 一帧处理）。需要更轻量时可选 [RNNoise](https://github.com/xiph/rnnoise)。
- 档位按终端配置：`off` / `mild` / `strong`。VAD 和唤醒阈值也按终端单独配置；现有 VAD 阈值 0.10 是按小爱麦克风调的，蓝牙麦克风需要重新调。
- 用数据决定档位：降噪开得过强会降低识别率和唤醒率。先录一组 20–30 句常用指令，在 1 米、3 米距离，安静和开电视或风扇各录一遍；离线对比 `off` / `mild` / `strong` 的 SenseVoice 识别错字率、唤醒命中和误唤醒次数，再定默认档位。
- 现有 20 秒录音 RMS -27.31 dBFS、峰值 -8.25 dBFS，电平正常。当时整段识别漏字，更可能是没有按句切分，不一定是噪声问题。
- 回声消除：电脑终端知道自己正在播放什么，有参考信号，以后可以做。但蓝牙延迟大且不稳定，第一版保持轮流听说，回声消除与语音打断放到后续阶段，先离线验证再上线。
- 小爱桥接本期不改。该模块以后也可用于小爱（其麦克风设备第 4 通道是播放回采），另行评估。

### 5.6 交互流程

```text
待机 / 本地唤醒检测
  → 唤醒提示音
  → 监听 / VAD 判句
  → 上传语音 / 等待 AI
  → 播放回答
  → 等待本地播放队列排空及短暂余音保护
  → 继续监听；超时返回待机
```

第一版采用轮流听说。播放时暂停语音触发，避免把自己的回答再次识别为输入；提供手动停止播放。服务端 `tts.stop` 不等于扬声器已经播完，恢复监听以本地播放完成为准。

连续语音打断作为后续能力，需要验证或补充回声消除、播放参考音频、延迟对齐和误触发控制，不能把普通麦克风支持等同于全双工可用。

各终端分房间使用，第一版各自独立；可配置相同唤醒词。将来出现明显串音时，再考虑不同唤醒词或跨终端唤醒仲裁。

### 5.7 Windows 运行会话与常驻

终端必须运行在能访问本机音频设备的会话里，常驻不能依赖远程桌面是否连接。两种方式由 P0.5 测试决定：

- 用户会话：控制台自动登录，计划任务在用户登录时启动守护程序；远程桌面客户端的远程音频设为“在远程计算机上播放”；断开远程桌面后如果音频受影响，用 `tscon` 把会话交回控制台。
- 会话 0 后台运行：之前在 SSH（会话 0）下用 FFmpeg 已能录音。如果 WASAPI 录音和播放在会话 0 都正常，可以作为不依赖登录的常驻方式。

另外关闭蓝牙适配器的“允许计算机关闭此设备以节约电源”。系统睡眠当前已经是“从不”。锁屏、注销、重启后的恢复分别验收。

## 6. 会话隔离、按来源返回与房间上下文

- 每个逻辑终端使用独立、持久化的 `Device-Id`，格式满足现有协议校验；显示名称与协议身份分开。
- 每终端独立 WebSocket。响应沿请求所属连接返回，不能用来源 IP 分流，因为多个终端可以位于同一主机。
- 当前对话、音频缓冲、播放队列、取消标记、超时与重连代次属于该终端。
- 断线后清理本地旧任务和音频，重连建立新会话；打断只影响发起打断的连接。
- 连接身份不等于身份认证；局域网复用现有认证配置，若后端要求 token，终端单独配置，不把凭证写入文档和日志。
- 家庭角色、技能和长期偏好可以复用，当前对话历史分别传递。当前 Hermes provider 不使用 `session_id`，已按连接隔离；以后若改为 Hermes 侧固定会话，必须按设备区分。
- 本地 ASR、TTS 或 Hermes 有资源排队时，可以排队计算，但不得混合两端数据或取消另一端任务。

房间上下文：

- 每台终端（包括小爱）在后端设备映射中登记所在房间，房间名与 Home Assistant 区域对应。
- 后端建立连接时，把“用户正在 <房间> 说话”写入该连接的系统提示；LLM provider 不需要知道设备身份。
- 未指明房间的指令（如“把灯打开”）按所在房间执行；用户明确说了其他房间时以用户说法为准。

## 7. 后端按设备选择 TTS

### 7.1 输出方式与合成引擎分开配置

| 终端与选择 | 后端响应 | 播放位置 |
| --- | --- | --- |
| 现有小爱 / 原生输出 | 文字及 TTS 生命周期事件 | 小爱 `mibrain` 合成、原生音色播放 |
| 普通终端 / Sherpa | 本地 Sherpa 合成并编码的 Opus 音频及事件 | 该终端绑定的扬声器 |
| 普通终端 / Edge TTS | 在线 Edge TTS 合成、后端转换为统一 Opus 格式后的音频及事件 | 该终端绑定的扬声器 |

实现方式：

- 后端维护设备映射表：`device-id` → 输出方式、合成引擎、音色、所在房间。
- 在连接初始化时决定：`device-id` 在创建 TTS 实例之前已读取，结果写入该连接自己的 TTS 实例，不在请求中修改进程环境变量。
- 未登记的设备沿用当前默认行为，保证小爱不受影响。
- 写成一个单独的 provider / 模块文件，像 `hermes.py` 一样通过卷挂载，不再往 `patch_index_stream.py` 里继续加字符串替换，降低后端升级时的破坏面。

建议的配置概念如下，属于待实现设计，不是当前配置文件已经支持的字段：

| 配置项 | 设计含义 |
| --- | --- |
| `room` | 终端所在房间，用于房间上下文 |
| `output_mode` | `native_xiaomi`：终端合成；`server_audio`：后端合成并发送音频 |
| `tts_provider` | 服务端音频选择 `sherpa` 或 `edge_tts`，与终端操作系统无关 |
| `voice` | 所选引擎的音色 ID，按设备保存和验证 |
| `rate` / `volume` / `pitch` | 引擎支持时允许设置；不支持的选项明确提示，不静默忽略 |
| `fallback_provider` | 可选的失败回退引擎；默认关闭，设备配置可以显式指定 |

现有代码把 `sherpa` 同时用作“接收服务端音频”的模式名称。实现时需保留旧名称的兼容映射，并区分输出方式与 TTS provider，避免加入 Edge TTS 后误走小爱文字合成路径。

未来可扩展 hello 中的终端能力协商；本期不依赖客户端自报能力自动改变所有连接的模式。初始化顺序需要确保选择发生在 TTS 输出之前，且握手和 TTS 线程之间不存在竞态。

### 7.2 Sherpa 与 Edge TTS

| 项目 | Sherpa TTS | Edge TTS |
| --- | --- | --- |
| 合成位置 | 本地后端 | Microsoft Edge 在线语音服务 |
| 使用成本 | 无按次云合成费用，使用本机计算资源 | 免费在线选项，无需 API Key |
| 网络与数据 | 合成可离线，不为 TTS 外发文本 | 需要联网，待播报文本发送到在线合成服务；该 TTS 流程无需上传麦克风录音 |
| 资源与音色 | 需要本地模型，使用已部署的 Sherpa 音色 | 后端调用 `edge-tts`，可枚举并选择在线音色 |
| 平台要求 | 后端模型和运行库兼容目标平台 | Python 模块不要求 Windows 或安装 Microsoft Edge |

[edge-tts 项目说明](https://github.com/rany2/edge-tts)确认其通过 Python 使用 Edge 在线语音服务，无需 Microsoft Edge、Windows 或 API Key。方案将其纳入免费在线选项；联网失败时按配置处理，不把在线合成当作离线能力。

两种引擎都放在小智后端，普通终端只接收统一的音频和事件，不直接依赖 Edge 服务或播放命令。这样更换终端系统或迁移后端时，保持相同的协议和设备路由。

仓库[现有部署说明](../deploy/sherpa-tts/README.md)已记录保留 `EdgeTTS` 配置及全局回退方法。P3 实施时优先复用小智后端现有 EdgeTTS provider，核对实际部署版本的能力；本次未切换或验证在线合成。

### 7.3 格式、取消和回退

- Sherpa 的 PCM 与 Edge TTS 的压缩音频由后端分别解码或转换为协商后的统一 PCM / Opus。不能把 Edge 返回的 MP3 数据直接当作 Opus 帧发送。
- MP3 解码、重采样等依赖放在后端，按实际 provider 需要配置 FFmpeg 或等价库；普通终端不因选择 Edge TTS 而新增专用播放器依赖。
- 按句合成并尽早下发，验证首次出声和句间停顿；复用 provider 前确认其是否真正支持流式输出，不把整句合成宣称为逐帧实时合成。
- 网络超时、取消、播放队列和临时文件都按连接及回答管理。一端调用 Edge TTS 失败或取消，不影响另一端的 Sherpa 或小爱原生输出。
- 可显式配置 Edge TTS 失败后回退 Sherpa。仅在该段尚未开始播放时重新合成该段；已经播放的内容不从头重播，取消的回答不得再触发回退。整段边界与已播放状态需要测试。
- 默认不自动把本地 Sherpa 请求切到在线 Edge TTS。在线引擎及回退由设备配置决定。

现有小爱保持原生音色；普通终端使用所选引擎的音色。现有全局切换脚本也需适配：加入混合终端后，不能一次切换把所有设备变成“只收文字”或覆盖其他终端的引擎。

## 8. 蓝牙硬件验证

输入测试结果单独记录在 [蓝牙音箱输入测试记录](bluetooth-audio-input-validation.md)。

传统蓝牙 A2DP 主要用于播放，使用麦克风会进入 HFP 通话模式。Windows 音频接口报告的 48 kHz 等采样率可能经过系统重采样，不能证明无线链路本身是宽带或高保真。

### 8.1 麦克风常开的影响

唤醒词要求麦克风一直打开，这意味着音箱会一直处在通话模式：

- 播放会降到单声道、通话音质（窄带约 8 kHz 或宽带 16 kHz 采样，取决于双方支持的编码）；
- 立体声输出端点可能被占用或改走通话输出；
- 之前的验收是分别测试播放和录音，还没测过“麦克风打开的同时播放”。

这是蓝牙终端的首要硬件风险，必须在写终端代码之前验证（P0.5）。

### 8.2 逐级判断

1. **枚举**：系统存在真正的蓝牙麦克风输入端点，而非 loopback、立体声混音或远程桌面重定向输入。（已通过）
2. **打开**：应用能打开指定输入，持续得到规定时长的采样，而非初始化成功后无数据。（已通过，FFmpeg）
3. **有效声音**：短录音不是全零，电平合理，无明显削波；区分底噪、敲击声和人声。（已通过）
4. **真人输入**：人在该音箱旁朗读约定短句，通过回听或本地 ASR 确认内容与位置。（已通过）
5. **常开录放**：麦克风打开期间播放，确认出声端点、音质和录音连续性。（P0.5）
6. **后续稳定性**：播放后恢复收音、蓝牙断开重连、距离变化、远程桌面断开、登录和休眠恢复。（P0.5 起逐项）

### 8.3 P0.5 测试项

| 编号 | 测试 | 要回答的问题 |
| --- | --- | --- |
| A | 麦克风关闭时向立体声输出播放 | 正常播放音质基线 |
| B | 麦克风连续打开 ≥30 分钟（之后延长到数小时），期间分别向立体声和 Hands-Free 输出播放自报端点名称的语音和扫频 | 哪个端点实际出声、音质能否接受、录音是否中断或掉帧 |
| C | 分别在会话 0（SSH / 后台）和用户会话枚举、录音、播放；远程桌面断开后重复 | 终端应该运行在哪个会话 |
| D | 音箱闲置后是否自动休眠，断电或关机后能否自动重连 | 常驻是否需要额外的重连逻辑 |
| E | 降噪对照语料：20–30 句常用指令，1 米 / 3 米，安静 / 有噪声 | 为 5.5 的档位选择提供数据 |

短录音及日志存放在临时诊断目录，原始环境音不提交 Git；默认不向外部转写服务上传。若使用 ASR，只调用已部署的本地识别能力，不把测试句子送入可执行智能家居动作的对话链路。P0.5 结果单独记录。

## 9. 实施与验收顺序

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| P0 已完成 | 本方案、Windows 蓝牙输入证据 | 指定设备已采集到 20 秒音频，本地 ASR 分段识别出真人测试内容，用户回听确认 |
| P0.5 | 第 8.3 节 A–E 测试，不写终端代码 | 测试记录；确定蓝牙终端使用的输出端点、常驻运行方式；得到降噪对照语料 |
| P1 | py-xiaozhi 验证；Windows 单终端单进程；直连后端；后端按设备 ID 选择输出方式（Sherpa 服务端音频）；轮流听说；按名称绑定设备 | 蓝牙音箱完成语音→ASR→AI→TTS→原设备播放的一问一答，小爱原生输出不受影响 |
| P2 | 音频前端（按语料对比选档）、唤醒与连续对话、断线重连、房间上下文、守护与开机自启 | 每端至少 10 轮；蓝牙和网络恢复后无旧语音残留；未指明房间的指令按所在房间执行 |
| P3 | 第二台终端（USB 电脑终端或 ESP32）并发；按设备 Edge TTS | 两端同时使用各自返回；一端中断不影响另一端；混用 TTS 引擎验收 |
| 以后 | 回声消除与语音打断、跨房间唤醒仲裁、macOS / Linux 验收 | 分别记录 |

自动测试覆盖会话隔离、设备选择失败、重连过期任务、格式转换、TTS 引擎混用、在线超时和取消后的音频清理。显式启用回退时验证不重复播报、不向其他设备返回。实际集成验收分别记录 Sherpa / Edge 的音色、首句延迟、长回答停顿、断网行为及设备路由。硬件验收覆盖实录、实播、回声和重连；模拟测试通过不能替代硬件验收。

部署时保存现有镜像和配置，新增终端独立启停。后端修改保持旧设备行为，必要时恢复原镜像及配置；小爱不需要再次刷机。Python 依赖、原生音频库、Opus 和模型资源按平台分别验证与打包。
